# Automated PR Responses

Draft each reply with clear authorship. Keep the user in control without requiring approval syntax or magic words.

## Bot begets Bot

Classify each review comment before drafting:

- **Automated review:** Treat a comment as automated when bot identity, disclosure, content, style, or surrounding context makes AI generation clear. Use practical judgment; metadata or explicit disclosure is not required.
- **Coworker-written review:** Treat a comment as coworker-written when it reads as personally authored and lacks strong signals of AI generation.
- **Uncertain:** Treat uncertain authorship as coworker-written.

The bot may draft and offer to post replies to automated reviews. For each coworker-written or uncertain review, surface a suggestion but flag the item. Require one of these paths before posting:

1. The user supplies a response in their own words. Treat it as the full human-authored reply unless the user asks to combine it with bot text.
2. The user gives item-specific permission for the bot to answer that coworker. Natural conversational approval is sufficient.

## Workflow

1. Read each PR comment and enough surrounding code or discussion to answer accurately.
2. Classify the comment source using **Bot begets Bot**.
3. Assign each draft item a stable one-based index. Show the original comment and source classification as approval context.
4. Draft the GitHub reply in the applicable format below.
5. If the user supplies text, copy it verbatim. Do not rewrite it unless explicitly asked.
6. Ask casually whether the ready items should be posted. Do not prescribe approval phrases.
7. Treat a natural affirmative answer to the immediately preceding posting question as approval for the items clearly named by that question. If scope is unclear, ask which items without requiring special syntax.
8. For a coworker-written or uncertain item, get the user's own response or clear item-specific permission for the bot suggestion. Batch approval for automated-review items does not include these items.
9. If a draft changes after approval, show the revision and ask again briefly.
10. Before posting, verify that each target comment and final reply match the approval view.
11. Post only the confirmed reply to its corresponding comment thread. Do not resolve the thread or perform another PR action unless separately requested.

Good approval questions are conversational: `Want these posted?` or `Item 2 looks coworker-written. Want to write the response, or should the bot post this suggestion?`

Do not say that the user must type `post`, `publish`, `send`, an item command, or another exact phrase. Replies such as `yes`, `sure`, `go ahead`, `looks good`, or `approved` authorize posting when they directly answer a clear posting question.

## Approval format

For an automated review:

```markdown
## Item 1

Source: automated review

Original comment (context only; omit from the GitHub reply):
> <original comment>

Proposed GitHub reply:
<optional verbatim user prefix>

[🤖 generated by <model number> - reviewed and approved by sawyer]

- <brief bot response without personal pronouns>
```

For a coworker-written or uncertain review:

```markdown
## Item 2

Source: coworker-written review
Needs: the user's own response or item-specific permission for the bot to answer

Original comment (context only; omit from the GitHub reply):
> <original comment>

Bot suggestion (not yet authorized):
[🤖 generated by <model number> - reviewed and approved by sawyer]

- <brief bot response without personal pronouns>
```

When the user supplies a response for a coworker-written item, replace the bot suggestion with a proposed GitHub reply containing only the user's verbatim text. Omit the bot tag unless the user explicitly asks to combine both voices.

Use indexes and source labels only in the approval view. Never include them in the GitHub reply.

Use the most specific model number exposed by the runtime. Do not invent a model number. If none is available, leave `<model number>` visible and flag it before approval.

## Relevance and brevity

- Answer the commenter's exact question or concern. Do not broaden the topic.
- Respect the commenter's intelligence. Do not explain concepts, code, or context already demonstrated in the comment.
- Default to one short bullet. Add another bullet only when it carries separate information needed to resolve the comment.
- Include only the direct answer, relevant change, supporting verification, or material limitation.
- Do not restate the comment, narrate the work, give an implementation tour, or add defensive justification.

## Voice and style

- Write bot-authored text without personal pronouns such as `I`, `me`, `my`, `we`, `us`, `our`, `you`, or `your`. Pronouns make the speaker ambiguous.
- Name the subject directly: `The validation now rejects empty IDs` or `The new test covers the failure path`.
- Do not claim the user's intent, judgment, or actions.
- Keep the response friendly, simple, and brief.
- Prefer bullets. Put one point or action in each bullet.
- Apply Simplified Technical English principles where practical: use familiar words, active voice, short sentences, and one meaning per word.
- State uncertainty and incomplete verification plainly.

The original comment, item index, source label, and approval notes are context only. Never include them in the GitHub reply. The user's verbatim text may contain personal pronouns; the restriction applies only to bot-authored text.
